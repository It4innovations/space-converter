# GPU Test Plan for space-converter

Purpose: everything a fresh session on a **GPU cluster** needs to verify the GPU
code paths of space-converter. Background: a large bug-fix pass (see
`docs/SpaceConverter_Code_Analysis_2026-08.md`, §12) was developed and verified
on a **CPU-only build** (Barbora, `WITH_GPU_CUDA=OFF`, `WITH_CUDAKDTREE=OFF`).
Several GPU files were modified **without being compiled**, so the first task is
simply to build them; after that, run the functional tests below.

The CPU-side behavior is covered by `tests/run_smoke_tests.sh` (T1–T9, all
passing on CPU); this plan adds the GPU-only coverage (the former "T7" and more).

---

## 1. What was changed in GPU code without compile verification

These files compile only with `WITH_GPU_CUDA=ON` (and/or `WITH_CUDAKDTREE=ON`)
and therefore have **never been compiled** since the changes. Expect possible
trivial compile errors first (typos, missing includes) — fix them before any
functional testing:

| File | Change (may not compile yet) |
|---|---|
| `src/common/convert_vdb_kernel.cu` | Removed dead params from `convert_iolib_to_grid_gpu` signature; added `atomicMinFloat`/`atomicMaxFloat` helpers; sparse + dense kernels now take `min_value_out`/`max_value_out` and track **per-particle** value extrema (CPU semantics); wrappers allocate/read back a 2-float `d_minmax` buffer; empty-rank sentinels are now `FLT_MAX/-FLT_MAX` |
| `src/common/data_cache.cu` | GPU radius sort switched to a `thrust::sort` comparator over **compact** ids (`d_radii_thrust[i]` indexed by id — valid only under the new compact-id convention); Morton-sort bbox loop iterates the compact array directly |
| `src/utility/cudakdtree_tool.cu` | k-NN cycling rewritten: persistent host candidate store `h_cand_all`, per-batch device staging, extraction ONCE after the last round; `ensure_device` grow-only allocator lambda; dead `#if 0` blocks removed |
| `src/common/sparse_common.cu` | (unchanged logic, but include-neighbors changed: `sparse_common.h` gained `clampCoord` used by `packCoord3`, compiled into device code — verify `__host__ __device__` correctness) |
| `src/common/convert_vdb_kernel.h` | Shared host/device code: `ifloor` used in `process_particle`/`fill_voxels`, non-finite radius guard, normalized-unit radius tolerance — compiled into `.cu` TUs |

Also relevant (compiled on CPU but with GPU-relevant semantics):

- `src/data_processing.cpp`: `copy_particles_to_gpu()` **moved after** the k-NN
  radius computation (GPU previously used stale hsml radii).
- `src/utility/dense_utility.h`: device `pow` (double) instead of `powf`.
- `src/utility/logging.cpp`: `LOG_MeasureStart/Stop` no longer call
  `MPI_Barrier` (they deadlocked runs where a measured section is entered by a
  subset of ranks).

## 2. Build matrix

Build A — CUDA GPU:
```
-DWITH_GPU_CUDA=ON -DWITH_CUDAKDTREE=ON -DWITH_OPENVDB=ON
(plus the usual TBB/OpenVDB paths; MPI with CUDA support if available)
```
Build B — CUDA-aware MPI variant (if the cluster's MPI supports it):
```
Build A + -DWITH_CUDA_AWARE_MPI=ON
```
Build C (optional, AMD clusters — LUMI): `-DWITH_GPU_HIP=ON` analog; the HIP
compat layer is `src/utility/gpu_device_compat.h` / `src/common/hip/`.

Use the site build script as a template (`scripts/space_converter/karolina/build_kar.sh`
or `lumi/build_lumi.sh`). **GPU binding**: 1 rank per GPU via the site's
`gpu_bind_*.sh` (note: `scripts/space_converter/polaris/gpu_bind_polaris.sh` is
new; `gpu_bind_bar.sh` now applies `% 4`).

## 3. Test data

Deterministic synthetic datasets are generated by `tests/gen_*.py` (pure
python stdlib) — copy the `tests/` directory; no real datasets needed. The
driver `tests/run_smoke_tests.sh` runs T1–T9 against `SC_BIN`; on a GPU build,
T5 (k-NN) activates automatically. Adapt the launcher inside the script if the
cluster is not Slurm (`launch()` function; PBS on Polaris → `mpiexec`).

## 4. GPU test matrix (run each, compare against the same binary's CPU run)

Conventions: `SNAP` = generated GADGET_SIMPLE snapshot
(`python3 tests/gen_gadget_simple.py $OUT/snap_test`), `BASE` =
`--data-type GADGET_SIMPLE --gadget-file $SNAP --output-path $OUT --grid-dim 64`.
"CPU reference" = the same command without `--gpu`. Compare RAW dumps with
`tests/compare_raw.py A.raw B.raw 1e-3` (GPU float order differs more than MPI
order; loosen tolerance if needed but investigate anything > 1e-2 relative).

### G1 — GPU sparse extraction equals CPU
```
space_converter $BASE --export-data 0 0 --gpu
```
- PASS: same `particles_count` (1000), same active-voxel count as the CPU run,
  reported `minI/maxI` equal to CPU within float tolerance.
- Regression target: per-particle min/max semantics on GPU
  (`convert_to_sparse_grid_gpu` + `d_minmax`) — before the fix GPU reported
  voxel-value extrema, so a systematic difference vs CPU means the fix
  regressed or did not compile in.

### G2 — GPU dense splat equals CPU
```
space_converter $BASE --export-data 0 0 --dense-type 6 --radius-const 2 --dense-file 1 --gpu
```
- PASS: RAW dump within tolerance of the CPU run; min/max equal (per-particle
  semantics); grid offset handling identical for a `--bbox` sub-region run
  (repeat with `--bbox 100 100 100 600 600 600`).

### G3 — GPU particle type > 0 (compact-id convention on device)
```
space_converter $BASE --export-data 1 0 --gpu            # sparse, halo type
space_converter $BASE --export-data 1 0 --dense-type 6 --radius-const 2 --dense-file 1 --gpu
```
- PASS: 500 particles, results match CPU. This exercises
  `d_particles_id_ordered_per_ptype` under the new compact-id convention (ids
  index the compact per-type device arrays) — the pre-fix behavior was
  out-of-bounds device reads for type > 0.

### G4 — GPU sorts
```
... --export-data 0 0 --dense-type 6 --radius-const 2 --dense-file 1 --gpu --sort-by-radius
... --gpu --sort-by-non-overlap
... --gpu --sort-by-radius --sort-by-non-overlap
```
- PASS: identical grids (within tolerance) to the unsorted `--gpu` run —
  sorting must only change iteration order, never the result. Exercises the
  rewritten comparator sort in `data_cache.cu`.

### G5 — cudaKDTree k-NN, single rank
```
... --export-data 0 0 --cudakdtree --calc-radius-neigh 6 --dense-type 6 --dense-file 1 --gpu
```
- PASS: finite (non-zero, non-NaN) min/max; radii > 0. Compare against
  `--cudakdtree-cpu` (host build of the same tree code) and `--nanoflann`
  (if built): densities should agree within a few percent.

### G6 — cudaKDTree k-NN with MPI cycling (THE big regression test)
```
mpirun -n 2 ... --cudakdtree --calc-radius-neigh 6 ... --gpu
mpirun -n 4 ... (same)
```
- PASS: results within tolerance of the 1-rank run of G5.
- Pre-fix symptom: **radius = 0 / rho = NaN for every particle** whenever
  world_size > 1 (candidate lists were zeroed every cycling round). The fix
  keeps per-query candidate lists on the host (`h_cand_all`) and stages
  batches; also test with `CUDAKDTREE_NUM_SPLITS=4` in the environment to
  exercise the batched path explicitly.

### G7 — stale-radius regression (upload ordering)
```
... --gpu --cudakdtree --calc-radius-neigh 6 --dense-type 6 --dense-file 1
```
- PASS: the GPU dense grid must differ from a `--radius-const`-style
  single-voxel deposit and match the CPU k-NN run — i.e. the k-NN radii
  actually reached the device. (Fix: `copy_particles_to_gpu()` now runs AFTER
  `calculate_radius_by_cudakdtree`; a regression re-introduces hsml-only radii
  on the GPU while the CPU run uses k-NN radii.)

### G8 — GPU reduction paths
- Build A (no CUDA-aware MPI): `mpirun -n 2 ... --gpu` dense → device grids are
  copied to host (`from_device`) before `MPI_Reduce`; compare to `-n 1`.
- Build B (`WITH_CUDA_AWARE_MPI=ON`): same run exercises `mpi_reduce` on device
  pointers and the sparse `serializeGPU`/`deserializeGPU`/`merge` RDMA path
  (`VoxelGPUManagerSortReduce`). Compare 1 vs 2 vs 4 ranks.
- PASS: rank-count invariance within tolerance for sparse AND dense.

### G9 — `--dense-loop-over-voxels` (voxel-centric GPU path)
```
... --gpu --cudakdtree --calc-radius-neigh 8 --dense-type 6 --dense-loop-over-voxels --dense-file 1
```
- PASS: qualitatively similar grid to the particle-centric G5 run (not
  identical — different estimator); finite values; no crash. Exercises
  `convert_to_dense_grid_loop_over_voxels_gpu` + the prebuilt float4 KD-tree
  (`build_voxel_kdtree`).

### G10 — GPU NanoVDB / CUB outputs
```
... --gpu --nanovdb --export-data 0 0        # .nvdb written, loadable
... --gpu --cub --export-data 0 0            # .cub written (CUB save is partly TODO — document actual state)
```
- PASS: files produced, `--nanovdb` output openable (e.g. via the bspace
  NanoVDB converter or nanovdb_tool). Note the addon now has a CUB guard.

### G11 — remote protocol with GPU server
```
space_converter --data-type GADGET_SIMPLE --gadget-file $SNAP --output-path $OUT --port 5000 --gpu
python3 tests/protocol_client.py <host> 5000 0 0
```
- PASS: client checks succeed (VDB magic, sane min/max) — same as CPU T8.

### G12 — determinism/robustness extras
- `--gpu` run repeated twice → grids within tolerance (atomic order varies).
- 0-particle type (`--export-data 3 0`) → clean empty result, no crash,
  min/max sentinels do not pollute the MPI reduction (FLT_MAX handling).
- Large grid `--grid-dim 512` dense → memory allocation errors are reported,
  not silent.

## 5. Known GPU-side gaps / TODOs (document, do not silently fix)

- `eCUB` finalize/save is partly TODO in `data_processing.cpp` (`use_cub`).
- Raw-particle export (`--raw-particles`) is not implemented on GPU
  (`convert_iolib_to_grid_gpu` prints an error).
- The k-NN density estimate uses the query particle's mass for all neighbors
  (documented approximation, see analysis doc §3.4) — CPU and GPU share it.
- `find_min_max` on `VoxelGPUDenseManager`/`VoxelGPUManagerSortReduce` is no
  longer used by the conversion wrappers (replaced by per-particle extrema);
  it remains for other callers — candidates for cleanup if unused.
- HIP build: `atomicMinFloat/atomicMaxFloat` use `atomicCAS` +
  `__float_as_int` — verify these intrinsics exist in the HIP compat layer
  (`gpu_device_compat.h`) or add equivalents.

## 6. Suggested workflow for the GPU session

1. Build A; fix compile errors in the §1 files (expect small ones; keep fixes
   minimal and English-commented).
2. Copy `tests/`, generate data, adapt `launch()` for the site scheduler.
3. Run the CPU-mode smoke suite with the GPU binary (sanity: T1–T9 must pass).
4. Run G1–G7 single-node; then G6/G8 multi-rank; then B-variant if available.
5. Record results in this file (add a "Results" section) and fix regressions;
   do NOT commit — leave changes for review (project rule).
6. Never run compute on login nodes; use the site's job system
   (`srun --jobid=... --overlap ...` on Slurm sites).
